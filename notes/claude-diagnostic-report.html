1 Executive Summary

Three changes would reduce token consumption and improve response quality more than any adjustment to CLAUDE.md:

No model routing — 100% Sonnet for everything

Every session uses claude-sonnet-4-6, including simple git operations, lookups, and reformatting tasks that Haiku handles correctly at ~5× lower cost. Conversely, complex architecture and security analysis sessions never used Opus. This is the highest-leverage optimisation available.

Iterative context feeding drives correction cycles

The most common failure pattern: requirements delivered across multiple turns rather than upfront. Each correction turn costs expensive output tokens. This is primarily a prompting habit, not a CLAUDE.md problem — but a short "front-load context" rule would reinforce the right behaviour.

Sessions run long without deliberate endings

The largest conversation is 28MB / 35 turns. Multiple sessions exceed 2MB. Only 16 /compact mentions across 161 sessions. No evidence of handoff-document discipline. Long sessions cost more and degrade response quality.

The current CLAUDE.md is well-written and concise. Most rules appear followed. The biggest gaps are what it doesn't say: nothing about model selection, session lifecycle, or context front-loading.

2 Scope & Methodology

Staged analysis following the diagnostic prompt specification:

  1. Inventory: Enumerated all 36 project dirs, 161 JSONL session files (excluding subagent files), 185MB total.
  2. Categorisation by metadata: Inferred task domains from directory names and sizes without deep-reading all files.
  3. Broad sampling: Selected 15 representative sessions across domains (large, medium, small; different project types).
  4. Deep analysis: Extracted correction messages from the 5 highest-correction sessions. Reviewed first-user-message task types across top 30 files by size.
  5. Signal assessment: Patterns flattened after ~12 sessions. No new failure modes emerged after that point.

5 Failure-Mode Analysis

FM-1: Iterative context feeding (most impactful)

Description: User delivers requirements across multiple turns rather than upfront. Each turn corrects or extends the previous one. Claude responds fully each time, producing expensive output for a partially-understood task.

Evidence: jflan/30525791 — booking system assumption corrected 3 separate times across the session. spaces-backend/8fb2bd47 — "re-review this PR based on the knowledge updates" sent after initial review was complete. open-ux-tools/eacfc1f5 — same bash script run 7 times as investigation iterated.

Root cause: Prompting habit, not a Claude failure. User thinks while typing rather than front-loading. CLAUDE.md has no rule reinforcing upfront context delivery.

Addressable via: CLAUDE.md rule + prompting discipline. Not a skill candidate.

FM-2: Wrong assumption about requirements

Description: Claude infers a requirement not stated and builds toward it. User corrects, requiring rework.

Evidence: jflan — Claude assumed a booking system was needed; user corrected "no booking system required" and had to repeat it. "Undo last changes regarding this" after incorrect Seascape Terrace changes.

Root cause: Under-specified prompts. The "Think Before Coding" rule covers this but the habit of asking clarifying questions before implementing isn't consistently applied.

Addressable via: Stronger "state assumptions before acting" enforcement. Already in CLAUDE.md — may need emphasis or example.

FM-3: Output format mismatch

Description: Output structure doesn't match what the user needed. Requires a follow-up correction turn.

Evidence: spaces-backend — "make these questions more developer friendly" after PR review questions were generated. AITools — output format adjustments on prompt review.

Root cause: Format not specified in the original request. "Act Directly" rule means Claude picks a format rather than asking.

Addressable via: Per-request format specification (not CLAUDE.md). Some skill templates could encode expected output format.

FM-4: Terminology / vocabulary drift

Description: Claude uses informal or abbreviated terminology where formal names are required.

Evidence: tools-suite — "ensure you use SAP Business Technology Platform instead of sap btp".

Root cause: Project-specific terminology not in global CLAUDE.md. Appropriate for per-project CLAUDE.md or AGENTS.md, not global config.

Addressable via: Per-project AGENTS.md. Not a global CLAUDE.md concern.

FM-5: Skill invocation overhead / friction

Description: Skill loading messages appear in conversation history as "corrections" (false positives in analysis), but the real pattern is skills loading correctly. No genuine skill misfire observed.

Evidence: tools-suite/9a3558a6 — finishing-a-development-branch skill loaded correctly. portainer/fdd62dcd — git-guardrails skill loaded.

Root cause: Not a failure mode. Skills are working as intended.

Addressable via: N/A.

Identified inefficiencies

No model routing — highest impact item

Every session uses claude-sonnet-4-6. Tasks like "switch to main, pull latest", simple lookups, reformatting, and issue listing could run on Haiku at ~5× lower cost with no quality loss. Complex architecture/security sessions never used Opus despite clear benefit. Estimated waste: significant — qualitative assessment only, no token counts in history.

Iterative context feeding — second highest impact

Each correction turn produces a full Sonnet response for a partially-understood task. The jflan booking system correction alone triggered 3 full response cycles. Across ~50% of sessions, this pattern adds at least 1–2 unnecessary output cycles per session.

Long sessions without deliberate endings

Only 16 /compact uses across 161 sessions (10%). The 28MB Jen session (35 turns) and multiple 3–5MB sessions suggest sessions running to degradation. Long sessions accumulate cached context cost and eventually degrade response quality. No evidence of handoff-document discipline.

Token Awareness rule not producing observable behaviour change

The existing "Token Awareness" CLAUDE.md rule says to offer a lighter alternative before large operations. No evidence of this happening in any sampled session — no "this will consume significant tokens, want a lighter approach?" messages observed. The rule is either being skipped or not triggering. Low ROI rule.

RTK hook is working correctly

RTK is installed and active. Shell command token savings are being realised transparently. No issues here.

CLAUDE.md token cost is low

The global config (~74 lines across 2 files) loads on every turn. This is an appropriate size. No sections are verbose enough to warrant removal purely for token cost.

Routing mechanism recommendation

Given current workflow patterns, the best path forward is per-session model selection — start each session with the model appropriate to the session's dominant task. This requires no tooling changes, avoids cache-busting mid-session, and is easy to adopt incrementally.

For the PR Review skill candidate: encode a preferred model in frontmatter (model: sonnet) so it never accidentally runs on a heavier model.

12 Highest-Priority Improvements

P1: Add model selection rule to CLAUDE.md

A short rule (3–5 lines) stating: use Haiku for simple tasks (git ops, lookups, reformatting), Sonnet for standard implementation/review, top tier for architecture/novel problems. Adopt per-session model selection as the primary mechanism. This is the single highest-ROI change available.

P2: Add session lifecycle rule to CLAUDE.md

A short rule: start a fresh session for a new task; if context exceeds 50+ turns, write a handoff doc and /clear. This directly addresses the long-session degradation pattern.

P3: Create a PR Review skill

Encode consistent review format (one-line per finding, severity-tagged, no praise, format: path:line: <severity>: <problem>. <fix>.). Skill declares model: sonnet. Evidence: 5+ sessions, format corrections observed. Expected saving: 200–500 tokens per session plus rework cycles avoided.

P4: Replace Token Awareness rule with concrete front-loading rule

Remove the existing Token Awareness rule (not working). Replace with: "Before starting a task, state what information would reduce back-and-forth. If a requirement is ambiguous, ask one clarifying question rather than assuming." This directly addresses FM-1 and FM-2.

13 Lower-Priority / Speculative Improvements

  • Issue Triage skill — worth creating once PR Review skill is validated. Similar pattern, medium frequency.
  • Shorten Goal-Driven Execution rule — the test-first framing is good but the multi-step plan template adds overhead for simple tasks. Candidate for trimming.
  • Review skills at next model release — existing skills (finishing-a-development-branch, git-guardrails, superpowers) were written for earlier model generations. Some instructions may now be default behaviour.
  • Branch Setup alias or skill — "switch to X, pull latest" is very common but very simple. A shell alias or 5-line CLAUDE.md shorthand may be cheaper than a full skill.
  • Research + Verify skill — could address FM-1 in debugging sessions by front-loading investigation structure. Low confidence — investigate further before building.

14 Evidence Limitations

  • Correction detection is approximate. The correction signal used keyword matching on user messages. Some false positives (shell output containing "no") were manually filtered. The true correction rate per session is qualitative, not measured.
  • Token counts not available. JSONL history does not include token consumption per turn. All cost estimates are qualitative. Statements like "~5× cost difference" are based on known Haiku/Sonnet pricing, not measured session data.
  • 15 of 161 sessions deep-read. ~90% of sessions were characterised from metadata only (directory name, file size, first user message). Failure modes in sessions outside the sample are unknown.
  • No timestamp data used. It's not clear whether model usage or behaviour has changed over time. The full history may contain older sessions with different patterns.
  • Effort levels not visible. The JSONL history does not expose the effort level used per session. Whether sessions were running at default, high, or max effort is unknown.
  • Subagent sessions excluded. Files in subagents/ subdirectories were excluded. These may contain additional patterns.
